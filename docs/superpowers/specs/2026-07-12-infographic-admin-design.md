# Infographic Admin Upload — Design

## Context

`MWAfamily-main` is a static Mobirise-generated site (no build tooling, no
backend) published from the public GitHub repo `dc18sagittariuz/MWAfamily`
via GitHub Pages. The homepage (`index.html`) has an infographic carousel
with 7 hardcoded `<img>` slides that currently must be edited by hand. The
site text states infographics are meant to update monthly
("อัพเดททุกวันที่ 1 ของเดือน").

Goal: let a single admin upload new infographic images (and delete old
ones) from a simple in-browser admin page, with the public carousel
reflecting the change automatically — without introducing a server or a
new third-party service.

## Approach

Browser-side GitHub Contents API integration. The admin page authenticates
with a GitHub personal access token (framed to the user simply as a
"password") and commits directly to the repo:

- a new image file under `assets/images/`
- an updated `assets/images/infographics.json` manifest (ordered list of
  carousel entries)

The public carousel on `index.html` fetches `infographics.json` at page
load and renders itself from it, instead of from hardcoded markup.

GitHub Pages rebuilds the site (~30–90s) after each commit, so changes
appear on the live site shortly after upload/delete — acceptable given the
monthly update cadence.

Rejected alternatives:
- **Third-party storage (Firebase/Cloudinary):** instant updates, but adds
  a new service/account to manage for no real benefit at this update
  frequency.
- **Serverless function backend:** more "real" auth, but requires
  migrating off/adding to plain GitHub Pages hosting — heavier than this
  project needs.

## Components

### 1. `assets/images/infographics.json` (new)

Ordered array, single source of truth for carousel contents:

```json
[
  { "file": "assets/images/6904.jpg", "alt": "Infographic" },
  { "file": "assets/images/6903.jpg", "alt": "Infographic" }
]
```

Seeded at implementation time with the current 7 carousel images in their
existing order.

### 2. `admin.html` (new)

Standalone page, not linked from site nav. Plain HTML/CSS/JS, no build
step — consistent with the rest of the site.

**Gate screen:**
- Single input labeled "Access Password" + "Unlock" button.
- Value is treated as a GitHub personal access token (scoped to just this
  repo, contents read/write permission — created by the admin in GitHub's
  settings, not generated by this feature).
- Validated via `GET /repos/dc18sagittariuz/MWAfamily` using the token as
  a Bearer credential.
- On success: token cached in `localStorage`; gate is skipped on future
  visits as long as it's valid. On failure: inline error, nothing stored.

**Upload UI:**
- File picker (images only) + "Upload" button.
- On file selection: client-side resize to max width 1600px, re-encode as
  JPEG (~0.82 quality) via `<canvas>`, with a preview thumbnail shown
  before confirming.
- On "Upload": generate a collision-safe filename (e.g.
  `infographic-YYYYMMDD-N.jpg`), PUT it to `assets/images/` via the
  Contents API, then GET the current `infographics.json` (for its `sha`),
  append the new entry, PUT the updated manifest.
- Status line reflects progress: "Compressing… → Uploading image… →
  Updating carousel list… → Done, live in ~1 minute."

**Current images + delete:**
- Fetches `infographics.json`, renders a thumbnail grid with a "Delete"
  button per entry (confirm dialog required).
- Delete removes the entry from the manifest (PUT updated JSON) and
  deletes the underlying image file from `assets/images/` via the
  Contents API's delete endpoint, so the repo doesn't accumulate orphaned
  files.

### 3. `index.html` carousel changes

- Hardcoded `carousel-inner` and indicator `<ol>` markup replaced with
  empty containers (`id="infographic-carousel-inner"`, etc.).
- New script (placed before the existing lightbox script) fetches
  `infographics.json`, builds carousel-item divs / indicators matching
  the current markup exactly (so existing CSS — fades, shadows, zoom
  cursor — keeps working unchanged), then initializes the Bootstrap
  carousel programmatically.
- After building the DOM, it hands off to the existing lightbox script,
  which already scans `.carousel-item .item-wrapper img` — no changes
  needed to the lightbox logic itself.
- If the manifest is empty/missing/fails to fetch, the whole carousel
  section hides itself rather than showing a broken/empty slider.

## Error handling

- **Admin page:** invalid/expired token → clear error, gate re-shown.
  Upload/API failures (rate limit, network, oversized file) → inline
  error with the raw reason, retry enabled. If the image upload succeeds
  but the manifest update fails, show a warning that the image was
  uploaded but the list wasn't updated, with a "retry list update"
  action — never silently lose track of an uploaded-but-unlisted file.
- **Public carousel:** any fetch/parse failure → hide the carousel
  section gracefully; no JS error surfaced to visitors.

## Testing

No build/test tooling exists in this project. Verification is manual:
load `index.html` locally to confirm the carousel renders correctly from
the manifest, and manually exercise the admin page's upload/delete flow
(ideally against a throwaway token/branch first) before relying on it
against the live repo.

## Out of scope (for this iteration)

- Reordering existing carousel images from the admin page (order is
  currently just upload order; can be added later if needed).
- Multi-admin accounts / role management — single shared token model
  only.
- Captions/alt-text editing per image — alt text defaults to a fixed
  string, matching current site behavior.
